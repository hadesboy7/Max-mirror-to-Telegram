# Известные ограничения

Честный список того, что MAX Mirror **не умеет** и почему. Это не список
недоделок — большинство пунктов невозможно обойти в текущей архитектуре.

## 1. У сообщений MAX нет идентификатора

Веб-клиент MAX не отдаёт в разметку страницы ни `id` сообщения, ни полную дату.
Проверено по дампам реальной страницы: нет ни `id`, ни `data-message-id`, ни
UUID, ни элементов `<time>`, ни атрибутов `title` с датой. В поле времени у
свежих сообщений стоит `ЧЧ:ММ`, у старых — дата вида «3 июл.».

Мост опознаёт сообщения по содержимому: **автор + текст (или ссылка на вложение)
+ строка времени**. Отсюда три следствия:

- **Восстановление после простоя ограничено видимым окном** (около 30 последних
  сообщений). Если мост не работал долго и за это время пришло больше, самые
  старые пропущенные вернуть нельзя — их уже нет в разметке страницы, а
  запросить «всё после метки» без идентификатора невозможно.
- **Два буквально одинаковых сообщения** от одного человека в одну минуту
  различаются только позицией в списке и могут быть спутаны.
- Абсолютной защиты от дубликатов не существует, см. пункт 3.

## 2. Имя автора не всегда доступно

MAX не выводит имя отправителя у сообщений **с вложением**. В таких случаях в
Telegram придёт «Кто-то» вместо имени. Это поведение самого веб-клиента MAX.

## 3. Telegram Bot API не даёт идемпотентности отправки

Если процесс будет убит **ровно** между успешной отправкой и записью об этом в
базу, заявка останется в состоянии «отправляется». По умолчанию
(`RESEND_STUCK_SENDING=1`) мост повторит отправку: потерять сообщение хуже, чем
получить его дважды. Переключается в `.env`.

## 4. Отложенная доставка вложений

Часть вложений достаётся только из живой страницы: карточка файла — нажатием,
стикер — снимком элемента, недогруженный альбом — чтением последнего блока.
Если доставка отложилась больше чем на `DOM_FRESH_SEC` (120 секунд по
умолчанию) — например, Telegram был недоступен или мост перезапускался, — к
странице уже не обращаемся: там другое содержимое, и можно прислать **чужое
вложение**. Вместо этого придёт текст с пометкой «вложение не удалось
получить». Подмена содержимого хуже отсутствия вложения.

## 5. Зависимость от вёрстки MAX

Мост читает страницу по селекторам CSS. Если MAX изменит вёрстку, чтение
сломается. Мост это замечает: если поле ввода на месте, а сообщений не видно
долгое время, он присылает предупреждение. Селекторы настраиваются в `.env`
без правки кода — см. `docs/TROUBLESHOOTING.md`.

## 6. Один мост — одна беседа

Каждый запущенный мост читает одну беседу (`MAX_URL`). Для нескольких бесед
нужно несколько копий с разными `USER_DATA_DIR` и `STATE_DB`.

## 7. Редкий случай: вытеснение из базы

База хранит последние `STATE_KEEP` событий (20 000 по умолчанию), старые
доставленные удаляются. Если такое сообщение каким-то образом снова попадёт в
видимое окно и мост при этом перезапускался, оно может быть переслано повторно.
На практике не встречается: мост проматывает ленту только вниз, и сообщение из
глубины истории в окно не возвращается. Последствие — один-два дубликата, не
потеря.

## 8. Направление Telegram → MAX

Реализовано, но **выключено по умолчанию** (`SEND_TO_MAX=0`) и слабо проверено.
Не считайте эту возможность надёжной.

## 9. Что не проверено автоматическими тестами

Тесты не запускают браузер и не обращаются в сеть, поэтому **не подтверждены**
автоматически:

- реальная загрузка вложений из web.max.ru;
- снимок беседы по кнопке;
- доставка QR-кода при разлогине;
- восстановление сессии MAX.

Эти возможности реализованы и работают в эксплуатации у автора, но проверяются
только вручную после установки.
